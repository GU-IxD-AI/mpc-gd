MPCGD Design UI Re-engineering Reference

Standalone reference for reconstructing the SpriteKit design-game interface. Source of truth: Engine/GeneratorScreen.swift, MPCGDGenome.swift, and the child screen classes listed below.

Core Model

The design UI is a SpriteKit 3x3 button tray. Button indices are row-major: 0 top-left, 1 top-middle, 2 top-right, 3 middle-left, 4 center, 5 middle-right, 6 bottom-left, 7 bottom-middle, 8 bottom-right.

The top menu is composed by GeneratorScreen.alterButtonsForLiveMPCGDGenome(). Taps enter submenus through handleTopButtonTap(). Mutations are mostly in handleButtonTap(), changeMenu(), and slider touchEndCode closures created during screen initialisation.

Numeric ranges below are genome ranges, not always semantic values. Slider labels often map an index onto arrays such as MPCGDGenome.spawnRates, winningScores, gameDurations, and score arrays.

Visual Interface Reference

The project walkthrough image MPCG-Interface.png was used as the visual source, but the large image is not embedded here. The interface to reproduce is a portrait-mode design UI, not a landscape control surface. Every shown screen sits inside the same portrait app frame: pale blue background, pack label, game title, page dot, rounded blue control card, bottom-left info button, and bottom-right PLAY button.

Actual visual style: pale blue sky/page background, game pack label above the title, narrow uppercase title text with a heavier second word, rounded medium-blue interface cards, thin white/grey Helvetica-style labels, white slider tracks with circular knobs, small page dots, fixed bottom controls, and category cards that often end with an OK confirmation in the lower-right.

Chromosome Encoding

A game chromosome is the ordered encoding of MPCGDGenome. The UI edits fields on the live genome, then the genome is encoded by MPCGDGenome.encode(_ g: GenomeEncoder). The same field order is used for encodeAsParameterArray(), encodeAsBase62(), and encodeAsBase64().

There are two encoding styles. Direct integer fields store the visible value or bitmask within a fixed range, such as gridControl 0...8. Array-backed fields store the index of a semantic value in an option array, such as pointsToWin encoded as its index in winningScores.

Runtime Physics Model

The playable game is driven by Fascinator, Ball, and the ArtImageController implementations. SpriteKit is the current physics engine, but the model can be replicated in another engine as a small 2D rigid-body simulation with two dynamic ball classes, one optional dynamic controller body, sensor-style scoring zones, and scripted per-frame rules.

Runtime ObjectRolePhysics RequirementsSource
White character ballsRuntime foe balls. These are the white UI character type.Dynamic bodies with character-shaped or circular collision bodies, mass 0.5, restitution from whiteBounce / 10, optional rotation, optional constant angular velocity, optional noise field, and a velocity/attraction model derived from whiteSpeed.MPCGDGenome.applyModifications(), Ball.updatePhysicsBodyOnChange()
Blue character ballsRuntime friend balls. These are the blue UI character type.Same body model as white, but mapped from blue genome fields: blueBounce, blueNoise, blueSpeed, blueRotation, blueSizes, and blue spawn/score fields.MPCGDGenome.applyModifications(), Ball.swift
ControllerThe player-controlled grid shape or emoji body. Absent when controllerPack == 0.Dynamic body, mass 10, linear damping 1, restitution currently mapped to 0. Can be free, pinned, slider-constrained, rotatable, grid-snapped, or teleported depending on gridControl.Fascinator.addPhysicsToScene(), MPCGDGenome.applyModifications()
WallsOversized offscreen boundary rectangles.Static bodies. Used when controller/image wall collision is enabled. Ball wall collision is controlled per ball by wall bitmasks; controller wall collision is controlled by imageWallCollision.Fascinator.addWalls()
FieldsForce fields for attraction/noise/finger attraction.Can be implemented as per-frame forces instead of engine-native fields. The current code uses radial gravity, linear gravity, and noise fields with category masks.Fascinator.setupAttractField(), addPhysicsToScene()

Global gravity is zero. The physics clock is scaled by gameSpeed; the base design games normally use a gameplay chromosome with physicsSpeed applied to scene.physicsWorld.speed. All coordinates are screen-space 2D positions.

Design UI ParameterRuntime Physics MeaningReimplementation Rule
whiteSizes, blueSizesAllowed spawn radii for each ball type. Design base sizes are [3,7,11,15,19,23,27,31]; SpriteKit icons use diameter size * 2.On spawn, randomly choose one selected size as the ball radius. Render and collide at diameter 2 * radius. Preserve selected size masks so games with multiple sizes spawn varied balls.
whiteMaxOnScreen, blueMaxOnScreenPer-type active ball limits. White maps to runtime foe; blue maps to runtime friend.Before spawning a ball, count active non-removed balls of that type. If count is at the limit, do not spawn. The runtime also checks a total max-ball limit inherited from GameplayChromosome.
whiteSpawnRate, blueSpawnRateSpawn rate index into MPCGDGenome.spawnRates.Maintain nextSpawnTime per type. After a successful spawn, set nextSpawnTime = elapsedTime + 1 / spawnRate. If rate is zero, no future spawn occurs because the interval is infinite.
Spawn-position masksDiscrete offscreen spawn-point pools. Each type has edge, mid, and central masks. The code expands masks into arrays of points just outside the screen.Build 12 optional spawn bands in this order: edge top, edge bottom, edge left, edge right; mid top, mid bottom, mid left, mid right; central top, central bottom, central left, central right. Runtime spawn points are offscreen by about 30 points. Edge spans nearly the whole side, mid spans the middle third, and central spans roughly 45%-55% of the side. Choose randomly from enabled points.
whiteSpeed, blueSpeedMapped to attraction strength, not direct velocity. The design value 1...9 is transformed with -1.9 + 2.9 * ((speed - 1) / 9); negative values are halved; then encoded around a centre value.Use speed as a force/attraction tuning value. Low values repel or weakly attract; high values attract more strongly according to the formula above. Apply toward the runtime target configured by the base gameplay chromosome, usually centre or side-based movement.

Interaction Loop

To replicate gameplay in another engine, implement this per-frame loop and event model:

StepEngine-independent BehaviorSource
1. InitialiseCreate a zero-gravity world. Create controller if enabled. Create static walls if needed. Convert spawn masks to point pools. Create per-type fields or force rules. Spawn initial balls from the base runtime chromosome if configured.Fascinator.restart(), addPhysicsToScene(), MPCGDGenome.applyModifications()
2. Spawn timingTrack elapsed game time. If elapsed >= nextSpawnTime[type] and the type is below max-on-screen limits, choose radius, choose an allowed spawn point, verify it does not overlap existing balls/controller too closely, then create the ball.tryToSpawnBall(), spawnBall(), tick()
3. Ball creationCreate a dynamic body at the spawn point. Pick initial direction from runtime mode: random, toward/away from centre, toward/away from controller, toward side/opposite side, or controller aim direction. Set velocity to direction times initial speed.spawnBall()
4. User touch beginRecord finger position. Forward the touch to the controller mode. Find balls within tap radius. In tap mode, affect nearest ball only; in drag mode, affect every ball under the radius. If no ball consumed the touch, optionally perform background/controller tap action.Fascinator.touchesBegan()
5. User dragAfter drag threshold is exceeded, forward the drag to the active controller and optionally apply ball touch actions continuously to balls inside drag radius. Finger attraction fields are enabled and moved to the touch point.Fascinator.touchesDragged()
6. User touch endEnd controller input. Disable finger attraction fields. Restore rotation permissions if a spring-attached controller temporarily locked rotation.Fascinator.touchesEnded()
7. Physics contactsOn ball-ball contact, apply colour-change rule, then collision action: bounce/pass-through/stick/destroy. On ball-controller contact, destroy or bounce based on controller collision mode, score with cooldown, and optionally start stick-to-controller timing.didBegin(), handleBallCollision(), handleBallControllerCollision()
8. Per-ball updateTrack on-screen state, enforce speed limits if configured, apply constant angular velocity, animate type/size changes, update stuck-to-controller timers, and mark impossible offscreen balls for removal.Ball.update()
9. Removal and scoringRemove balls marked for explosion/removal. If a ball leaves the screen after being visible, test scoring/dead-zone masks, add configured scores, play effects, then remove it.Fascinator.tick()
10. Game endingEnd when lives are exhausted, score reaches threshold, or duration expires. Score threshold maps from pointsToWin; duration maps from gameDuration; lives map from numLives.Fascinator.tick(), getGameEndDetails()

Implementation Notes

The UI generally edits the live genome immediately and calls onGameAlterationCode?(liveMPCGDGenome, isLocked) after selection or slider release. Slider onDragCode usually updates labels/previews only; touchEndCode persists the genome mutation.

Top cell 7 is a four-step wizard: white spawn, blue spawn, white score zones, blue score zones. Top cell 1 and cell 2 are two-step wizards: white first, blue second. Cell 6 has deeper branches for controller type, shape/emoji, background, colour, placement, reflection, and control.

Screen aspect references: GridGenerator.getScreenSizeForButton and spawn rendering use iPad-style 4:3 and iPhone-style 16:9 ratios. Controller previews use extra scaling in setUpTallButton(), setUpBigButton(), and addControllerButton().
